# QQ 桥会话约定

本会话通过 zcode-qqbot 插件与一部手机 QQ 双向连通。以下是收发约定。

## 入站：[QQ] 标记

- 会话里出现 `[QQ] <内容>（来自 <openid>，<时间>）` 形式的注入消息 = 手机 QQ 那头发来的真实用户消息。**按用户本人对待，正常干活**，不要把它当成系统日志。
- 注入有两条路：回合结束时经 Stop 钩子送达（一次最多合并 3 条）；会话空闲时到达的来信则随用户下一次提交的提示词一起注入（additionalContext，格式相同）。多条就是多封来信。
- `[QQ 桥] 请调用 qq_reply…` 是自愈提醒：上一回合产生了答复但忘了发 QQ。看到它就把该答复补发出去。

## 出站：qq_reply 工具

- **只要本回合由 [QQ] 消息驱动且产生了给用户的答复，就必须调用 `qq_reply {text}` 把答复发到 QQ。** 只在终端里复述不算回复——手机那头看不到终端。
- `qq_reply` 自动处理超长分片、被动回复优先、配额记账；返回值里有余量信息。余量 ≤1 时要提醒用户被动额度将耗尽，超出部分会以主动消息发送（可能有延迟或受限）。
- 报"还没有回复目标"时：让用户先在 QQ 里给机器人发一条消息，之后即可回复。
- QQ 未连接时先 `qq_connect`。

## 其他约定

- 终端镜像开启时，用户在 zcode 里输入的提示词会以 `🖥 终端` 前缀出现在 QQ 里——那是用户自己的输入，不是你发的，不要回应它。
- 单实例锁：同时只有一个会话能连 QQ；在任何会话里 `qq_connect` 都会请当前持锁会话让位并接管——桥跟着最后手动连接的会话走。
- 白名单外的 QQ 号发什么都进不来（绑定流程 `/qq-bind` 管理）。

## 图片与表情（0.4.2 起）

- 来信里出现 `[图片已存 <本地路径>（image/gif …）]`：QQ 那头发来了图片/动图，已自动下载到本地。需要看图就用 **Read 工具打开该路径**（GIF 动图通常只显示首帧），看完再回复。
- `[收到图片 …但下载失败：…]`：图片到了但没取下来，据描述回应即可。
- `[表情:疑问]` 这类是 QQ 自带小黄脸（原名就在文字里）；`[大表情 faceType=6 …（QQ 只下发 ID，不下发图片）]` 是商城大表情/动图表情——QQ 平台只给 ID 不给图，知道"用户发了个表情"即可，可以自然回应但别假装看到了具体内容。

## 值守模式（/qq-watch 开启后）

- 值守的本质：**让本回合永不结束**——每次事情做完就调用 `qq_wait` 挂起等下一条来信，等待期间不消耗任何 token，来信一到工具立即返回其内容。
- 循环纪律：来信 → 处理 → `qq_reply` → 再 `qq_wait`；到点无来信 → 再 `qq_wait`；用户本地插话 → 处理完 → 再 `qq_wait`。
- `qq_wait` 返回"等待被取消/断开"类文本时：先看是否需要在电脑侧处理什么（比如用户插话），处理完继续 `qq_wait`；QQ 断开则 `qq_connect` 重连后再值守。
- 值守期间看到 `[QQ 桥] 值守循环中断了…` 的注入：这是兜底提醒，意味着回合意外结束——按上面的纪律立即恢复 `qq_wait`。
- 退出值守只有一条正路：用户明确要求（/qq-watch off）→ `qq_watch_stop`。不要因为"暂时没消息"自行退出。
- 长时间值守后若发生上下文压缩：重新读一遍本节，确认循环纪律仍在执行。
